PIPELINE OVERVIEW (context only — this already exists in the codebase)
=====================================================================
The TestGen pipeline takes a JML-style API specification + a "test string"
(sequence of method calls) and produces:
  1. An ATC (Abstract Test Case) Intermediate Representation (IR)
  2. A Symbolic IR (for Symbolic PathFinder / SPF-style symbolic execution)
  3. Generated Java code, in TWO flavors:
       a. SPF file — uses symbolic placeholders (Debug.makeSymbolicString /
          Debug.makeSymbolicInteger / Debug.makeSymbolicRef) so a solver can reason
          about postcondition constraints.
       b. JUnit file — uses DYNAMIC BINDING: discards the symbolic placeholder and
          instead calls executeApiCall(...) then extractFromResponse(...) to get the
          REAL return value from the library/server at runtime.
  4. Correct handling of SERVER_OUTPUT values (values the callee/library generates,
     e.g. from push/pop, put, submit) as they propagate across the sequence of calls.

This must work correctly across 3 validation examples (below) which stress different
edge cases of return-value propagation. Use these as your test fixtures / acceptance
tests.

=====================================================================
1. CORE TERMINOLOGY
=====================================================================
- CLIENT_INPUT: a value the caller supplies (e.g. element to push, key to look up,
  a submitted payload). Comes from Symbolic.input() / Debug.makeSymbolic*.
- SERVER_OUTPUT: a value generated by the callee (library/server) at call time that
  the caller could not have known in advance (e.g. popped element, old value from
  put, auto-assigned task ID). Captured from the return value of execute()/the API
  call.
- \result: JML-style notation for "the return value of the function", used in
  postconditions.
- _old suffix: snapshot of a global/parameter's value BEFORE the call (e.g. size_old,
  M_old, Tasks_old).
- dom(M): domain (key set) of a map M.
- AtcReturnCaptureStmt: IR node that replaces a method call in a "producing" block —
  captures the SERVER_OUTPUT into a named variable.
- AtcPropagatedInputStmt: IR node that replaces a symbolic declaration in a
  "consuming" block — the value is passed in as a parameter (arrived from an earlier
  block's SERVER_OUTPUT), not freshly declared.
- availableServerOutputs: running set (during the propagation scan) of SERVER_OUTPUT
  variable names produced so far in the test string.
- propagatedParamsPerFunc: map from function name -> set of parameter names it
  receives that were propagated from an earlier SERVER_OUTPUT (name-matched).

=====================================================================
2. ALGORITHM STEPS (NewGenATC)
=====================================================================
STEP A — Propagation Scan:
  Walk the test string block by block, in order. Maintain availableServerOutputs.
  For each block (function call):
    - If a formal parameter of the function NAME-MATCHES a variable already in
      availableServerOutputs, mark it as a propagated parameter (do NOT re-declare
      it as fresh symbolic input in this block; add it to the helper's parameter
      list instead).
    - If the function's postcondition binds \result to some variable, that variable
      is SERVER_OUTPUT. Add it to availableServerOutputs after this block.
    - NOTE: propagation is by VARIABLE NAME MATCHING ONLY (known limitation — see
      Section 6, limitation #3). If upstream output is named `taskId` and downstream
      param is named `id`, no propagation is detected.

STEP B — ATC IR generation (per block):
    <type> <input vars> := input()      // CLIENT_INPUT, only if NOT propagated
    assume(<preconditions>)
    <snapshot old-state vars>            // e.g. size_old := size, M_old := M
    [<outputVar> := execute(<call>)]     // only if function has \result binding
                                          // (SERVER_OUTPUT capture)
    [<call>(<propagated + input args>)]  // if no \result binding
    assert(<postconditions, using \result / outputVar / old-state vars>)

STEP C — Symbolic IR generation (transform ATC IR):
    - For every declared CLIENT_INPUT var -> Debug.makeSymbolicString(name) /
      Debug.makeSymbolicInteger(name) / etc., matched to its declared type.
    - For every SERVER_OUTPUT var about to be captured -> PREPEND a symbolic
      placeholder declaration of the correct type BEFORE the call:
        String x = Debug.makeSymbolicString("x");      // for String
        Integer x = Debug.makeSymbolicInteger("x");    // for Integer (boxed)
        <T> x = Debug.makeSymbolicRef("x", null);       // fallback for other
                                                          // object/collection types
      NOTE: Integer must use makeSymbolicInteger, NOT makeSymbolicRef — TypeMapper
      must special-case boxed primitives (isCollectionType should exclude Integer,
      Long, Double, Boolean, etc., and route them to the primitive-symbolic path).
    - For AtcPropagatedInputStmt vars -> emit a FRESH symbolic variable of the same
      name/type (the solver enforces equality across blocks via assume() constraints
      on domain membership, e.g. assume(Tasks.containsKey(taskId))), rather than
      threading the literal captured object through the symbolic solver.
    - Every SERVER_OUTPUT capturing method call ends with `return <var>;` so callers
      (main()) can chain the value forward.

STEP D — Java Code Generation (two outputs from the same Symbolic IR):
    (a) SPF FILE (GeneratedATCs.java):
        - One helper method per block. Return type = capture var's type, or void if
          no capture.
        - Parameters = only the propagated vars (name-matched from upstream blocks).
          No-parameter functions get no formal parameter list, even if they return
          a value (see Example 1: pop_helper(), peek_helper()).
        - Body uses the Symbolic IR from Step C verbatim (symbolic placeholders +
          direct Helper.<method>(...) call).
        - main() instantiates the class, calls helpers in test-string order, and
          threads any propagated values as arguments to later helper calls.

    (b) JUNIT FILE (GeneratedATCs_JUnit.java) — DYNAMIC BINDING:
        - Same method signatures (name, return type, parameter list) as the SPF file.
          Only the BODY differs.
        - Discard the symbolic placeholder entirely. Instead:
              Response xResponse = executeApiCall(Helper.<method>(<args>));
              <Type> x = extractFromResponse(xResponse, "x");
        - Assertions remain, checked against real post-call state.
        - Nullable SERVER_OUTPUTs (e.g. HashMap.put's old value) must NOT get a
          spurious non-null assertion — only assert what the spec's postcondition
          actually constrains.

INVARIANT TO ENFORCE (and to unit-test): for every method, the SPF and JUnit
versions must have IDENTICAL signatures (name, return type, parameter list) and
IDENTICAL assertions; only the internal mechanism for obtaining the return value
differs (symbolic placeholder vs. real dynamic extraction).

=====================================================================
3. DATA MODEL / TYPES TO IMPLEMENT
=====================================================================
- VariableOrigin enum: { CLIENT_INPUT, SERVER_OUTPUT }
    Applies uniformly to primitives and object/reference types.
- Variable: { name, type, origin, nullable(bool) }
- JmlFunctionSpec: { name, params[], precondition, postcondition,
    resultBinding (nullable — the variable name bound to \result, or null if the
    function has no \result binding) }
    - detectResultBindings(): parses the postcondition text/AST and automatically
      finds "\result = <var>" without requiring manual annotation. Must work for
      both String-typed and Integer-typed (and generally any typed) bindings.
- AtcStatement (IR node base) with concrete subtypes including at least:
    - AtcInputDecl (CLIENT_INPUT declaration)
    - AtcAssume
    - AtcSnapshot (old-state capture)
    - AtcReturnCaptureStmt (replaces a call in a producing block; holds outputVar)
    - AtcPropagatedInputStmt (replaces a symbolic decl in a consuming block; holds
      the propagated var name + source block)
    - AtcAssert
- NewGenATC (driver): runs Step A (propagation scan) across the test string and
  builds the forwarding map (propagatedParamsPerFunc / availableServerOutputs),
  then drives IR generation and helper/main-method assembly.
- AtcIrToSymbolicIrTransformer: implements Step C.
- AtcIrCodeGenerator: implements Step D, emitting both SPF and JUnit variants from
  one shared Symbolic IR / method signature model.
- SpfWrapper: resolves and invokes the correct target helper method dynamically
  (including overloads distinguished by parameter type, e.g.
  getResult_helper(java.lang.Integer)) and is responsible for saving/writing both
  the SPF file and the JUnit file to disk.

4. VALIDATION EXAMPLES (use as fixtures / golden tests)
=====================================================================

--- EXAMPLE 1: Stack<String> ---  (pattern: independent captures, no propagation)
Global state: S: List<String> = [], size: int = 0
API:
  push(elem): pre elem != null; post S' = S+[elem], size' = size+1. No \result.
  pop(): pre size>0; post \result = poppedElem, S' = S[0..size-2], size' = size-1.
  peek(): pre size>0; post \result = S[size-1] (identity unknown beforehand),
          S' = S, size' = size.
Test string: push -> push -> pop -> peek
Expected behavior:
  - pop() and peek() each independently capture a SERVER_OUTPUT
    (poppedElem, peekedElem) with NO propagation between them (peek takes no
    params, so the propagation scan must NOT try to forward poppedElem into it).
  - Both helper methods have NO formal parameter list, despite returning a value.
  - main() calls both helpers and stores results independently.
  - Symbolic placeholder types: both String -> Debug.makeSymbolicString.

--- EXAMPLE 2: HashMap<String,Integer> ---  (pattern: nullable, produced-but-unconsumed)
Global state: M: Map<String,Integer> = {}, size: int = 0
API:
  put(key, value): pre key!=null, value!=null;
    post \result = oldVal, M'[key]=value, size' = size + (1 if key not in dom(M) else 0).
    oldVal is nullable (null if key was not previously present).
  getOldValue(key): pre key in dom(M); post \result = M[key]. Read-only.
  remove(key): pre key in dom(M); post M' = M \ {key}, size' = size-1. No \result.
Test string: put -> put -> getOldValue -> remove   (2nd put uses SAME key as 1st)
Expected behavior:
  - oldVal_0 (from block 0) is captured but the postcondition places NO
    non-null constraint on it -> code generator must NOT emit an assertion
    requiring oldVal_0 != null.
  - oldVal_0 and oldVal_1 are both "produced but not consumed": they enter
    availableServerOutputs but no downstream function has a same-named parameter,
    so neither is threaded forward as an argument. They ARE still returned from
    their helper methods (for potential caller-side use / assertions), just not
    passed as args elsewhere.
  - key is CLIENT_INPUT (not SERVER_OUTPUT) and is reused by name across
    put/getOldValue/remove blocks; each block independently declares a fresh
    symbolic string for key, and the solver enforces cross-block equality only
    via assume(key in dom(M))-style constraints — do not try to literally share
    the object.
  - Integer return type -> use Debug.makeSymbolicInteger for the SERVER_OUTPUT
    placeholder (oldVal, curVal), not makeSymbolicRef.

--- EXAMPLE 3: TaskQueue ---  (pattern: full multi-hop forward propagation)
Global state: Tasks: Map<Integer,String> = {}, Results: Map<Integer,String> = {},
              nextId: int = 1
API:
  submit(payload): pre payload!=null;
    post \result = taskId, Tasks'[taskId]=payload, nextId' = nextId+1.
  getResult(taskId): pre taskId in dom(Tasks); post \result = result,
    Results'[taskId] = result. taskId is SERVER_OUTPUT propagated from submit.
  cancelTask(taskId): pre taskId in dom(Tasks); post Tasks' = Tasks \ {taskId}.
    taskId is SERVER_OUTPUT propagated from submit.
Test string: submit -> getResult -> cancelTask
Expected propagation-scan trace (must match exactly):
  step 1 submit:     availableServerOutputs(after) = {taskId}       propagated = {}
  step 2 getResult:  availableServerOutputs(after) = {taskId,result} propagated = {taskId}
  step 3 cancelTask: availableServerOutputs(after) = {taskId,result} propagated = {taskId}
Expected behavior:
  - taskId (Integer, SERVER_OUTPUT) is threaded across TWO hops: submit ->
    getResult -> cancelTask. getResult_helper(Integer taskId) and
    cancelTask_helper(Integer taskId) both take taskId as a formal parameter.
  - result (String, SERVER_OUTPUT from getResult) enters availableServerOutputs
    but is NEVER consumed downstream (cancelTask has no `result` param) — captured
    and returned from getResult_helper, but not forwarded further. Must not error
    or force propagation.
  - main() must thread taskId as an explicit argument into both subsequent helper
    calls: 
        Integer taskId = instance.submit_helper();
        String result = instance.getResult_helper(taskId);
        instance.cancelTask_helper(taskId);
  - This example is structurally identical to a placeOrder -> shipOrder REST
    pattern — use it to confirm the algorithm is domain-agnostic (works the same
    whether the callee is a Java library or an HTTP API).

=====================================================================
5. CROSS-EXAMPLE INVARIANTS TO TEST
=====================================================================
1. No-parameter SERVER_OUTPUT functions (pop, peek) must generate helper methods
   with empty parameter lists even though they return a value.
2. Nullable SERVER_OUTPUT (put's oldVal) must use an object/boxed type (Integer,
   not int) so null is representable, and must not get a spurious non-null assert.
3. Produced-but-not-consumed SERVER_OUTPUTs must remain valid: captured, returned,
   but never forced into a downstream parameter list.
4. Full multi-hop propagation (TaskQueue) must correctly thread a SERVER_OUTPUT
   through 2+ consuming blocks.
5. SPF file and JUnit file must have IDENTICAL method signatures; only bodies
   differ (symbolic placeholder + direct call vs. executeApiCall +
   extractFromResponse).
6. Old-state snapshot variables (size_old, M_old, Tasks_old) are treated as
   ordinary (CLIENT_INPUT-class / non-\result) locals and handled by the existing
   snapshot mechanism without special-casing.
7. Boxed-primitive SERVER_OUTPUT (Integer) routes to makeSymbolicInteger, never to
   the generic makeSymbolicRef fallback path.

=====================================================================
6. KNOWN LIMITATIONS TO DOCUMENT (NOT necessarily to fix, but flag in code/comments)
=====================================================================
1. Auto-increment global counters (e.g. nextId): the symbolic solver cannot infer
   the concrete SERVER_OUTPUT value unless the counter itself is also modeled as a
   symbolic integer with constraints. Out of scope unless explicitly requested.
2. Custom (non-primitive, non-collection) return types fall back to
   makeSymbolicRef, which may under-constrain individual fields. Flag with a
   TODO/comment when this fallback path is hit.
3. Propagation is purely name-based. If spec authors use inconsistent names for
   the same semantic value across blocks (e.g. `taskId` upstream vs `id`
   downstream), propagation silently fails. Consider emitting a warning when a
   function parameter's type matches an available SERVER_OUTPUT's type but the
   name does not, as a hint to the spec author (optional enhancement).
4. Multi-valued returns (tuples/records, e.g. login() -> (token, HttpStatus)) are
   NOT supported — AtcReturnCaptureStmt only holds a single bound name. Extending
   to a list of bound names is future work; do not attempt unless asked.
